# deck-remote

A phone remote control for **Google Slides or PDF decks open in Chrome**.

**Docs, live demo and connect helper:** https://diegoforni.github.io/deck-remote/

The tool runs on the computer that shows the deck. It drives the Chrome tab
over the DevTools protocol and serves a mobile web app on your Wi‑Fi (QR code
in the terminal). The phone gives you:

- **Multiple phones at once** — every connected phone (same Wi‑Fi or across the
  internet) sees the same live state, can press Next/Back, and the status bar
  shows how many phones are connected.
- **Next / Back buttons** that control the actual Chrome tab (real key events,
  so presenter view, transitions and embedded video all behave normally).
- **A talk timer** that starts on your *first press of Next* and keeps
  counting (with a reset button). It survives page reloads on the phone.
- **1–5 words describing the current slide**, and the next slide's full
  description as a heads-up — generated by a local **Gemma 4 E2B** vision
  model (llama.cpp) that reads the whole slide: text, charts and images, and
  answers in the slide's own language.
- **Live sync without flicker**: the deck is tracked with Chrome's screencast
  stream (frames arrive only when the page repaints — deck-remote never
  forces captures during your talk, so fullscreen Chrome doesn't flash).
  PDFs additionally use the viewer's `#page=` URL. Advance from the laptop
  keyboard or a USB clicker and the phone follows instantly.

```
Computer (deck in Chrome)          Phone (same Wi‑Fi)
┌───────────────────────┐          ┌──────────────────┐
│ Chrome ← keys (CDP)   │◀── WS ──▶│ Next / Back      │
│ screenshots + OCR     │          │ timer, keywords  │
└───────────────────────┘          └──────────────────┘
```

## Phones on ANY network (relay mode)

By default phones must reach the presenting computer directly (same Wi‑Fi,
hotspot, or a VPN like ZeroTier). For phones on **any network** — cellular,
guest Wi‑Fi with client isolation, another continent — run the relay on any
host with a public address (a cheap VPS is plenty; it relays only small JSON
messages, never slide images):

```bash
node relay.js --port 8676          # on the public host; open the port in its firewall
```

Then start the presenter with the relay address:

```bash
./deck-remote --relay ws://<relay-host>:8676 --url ~/deck.pdf
# add --relay-pin 4321 so remote phones also need a PIN
```

deck-remote connects **outbound** to the relay (no ports opened on the
presenting machine), prints a **second QR code** whose URL works from any
network, and keeps both local and remote phones in sync. Room codes rotate
each session; combine with `--relay-pin` on untrusted networks. If the relay
connection drops, it reconnects automatically and re-binds the same code.

## Requirements

- macOS (Apple Silicon or Intel) or Linux on the presenting computer
- ~7 GB of disk for the AI model + ~8 GB RAM recommended
- Chrome or Chromium (installed by you; the tool finds it, or `--chrome-path`)
- A phone on the same network (Wi‑Fi / hotspot)
- Internet once, for the installer

## Install (one line)

After copying/scp'ing this folder to the presenting machine:

```bash
bash install.sh
```

That's it — it installs Node.js LTS via nvm if missing (no sudo), (re)installs
dependencies cleanly, downloads **llama.cpp** and the **Gemma 4 E2B** vision
model (~6.2 GB, one time, resumable), and finishes with a live smoke test of
the model. Re-running is always safe and resumes partial downloads.

To copy the project over (no `node_modules`/model needed, they're reinstalled):

```bash
scp -r deck-remote/ diegoforni@desktop:            # or scp the tarball below
```

## Quick start

```bash
./deck-remote --url ~/talks/my-deck.pdf           # PDF: a path opens it automatically
./deck-remote --url docs.google.com              # or pick a tab by URL substring
```

Then:

1. The tool opens its own Chromium window (a dedicated profile under
   `~/deck-remote-chrome-profile`). Open your deck **in that window**:
   - **Google Slides**: sign into Google once in that window, open your deck,
     and press `Ctrl+F5` (⌘F5 on Mac) to enter presentation mode.
   - **PDF**: just open the file (`file://…` or a download works).
2. In the terminal, scan the printed **QR code** with your phone.
3. deck-remote does **one automatic pass** through the deck (it flips through
   every slide, screenshots and OCRs them, then returns to slide 1). Keep the
   deck in presentation mode and don't touch the mouse during this pass.
4. Present. Put Chrome in fullscreen (`F11`) for a clean look. The phone's
   timer starts the first time you press **Next**.

### Attaching to your existing Chrome instead

If you want to control a tab in your normal Chrome window (keeping your
logins), quit Chrome completely and relaunch it with a debug port:

```bash
google-chrome --remote-debugging-port=9222          # Linux
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --remote-debugging-port=9222   # macOS
```

Notes:

- Chrome 136+ **blocks** the debug port on the *default* profile. Either use
  `--user-data-dir=$HOME/chrome-debug-profile` (sign in once there), or use
  the tool's own window as described above.
- If the debug port is already open, deck-remote attaches and never launches
  its own window. Use `--list-tabs` to see what it can see, and `--url
  <substring>` to pick a tab non-interactively.

## How slide descriptions are made

During the setup pass, every slide's frame is sent to a **local Gemma 4 E2B**
vision model running in llama.cpp (started automatically by deck-remote, port
8128). The model reads the whole slide — all text plus charts and images —
and answers with the most helpful **1–5 word** description, **in the slide's
own language**; the phone shows the next slide's full description as the
heads-up. Descriptions are generated in the background (current slide first),
so you can start presenting before every one is ready. On first launch the
model takes ~a minute to load; each slide then takes a few seconds on Apple
Silicon.

If llama.cpp or the model are unavailable, deck-remote falls back to a
built-in OCR heuristic (biggest text → up to 5 words) and says so in the
logs. `--no-vlm` skips the model entirely.

## No-flash tracking

Older versions polled the deck with screenshots, which can make fullscreen
Chrome flash on macOS. Tracking now uses Chrome's screencast stream: frames
arrive only when the page repaints, so there are **zero forced captures**
during your presentation (the logs confirm: "Screencast tracking active").
PDFs are tracked via the viewer's `#page=` URL. If a browser doesn't support
screencast, deck-remote automatically falls back to screenshot polling.

## Options

```
--url <url|path|substring>  A local file path (pdf/html) or absolute URL is opened
                            automatically; otherwise a substring matched against
                            open tab URLs (e.g. docs.google.com)
--port <n>            HTTP/WS port for the phone UI (default 8675)
--debug-port <n>      Chrome DevTools port (default 9222)
--pin <code>          Require a PIN before a phone can connect (recommended on shared Wi‑Fi)
--no-vlm              Use the built-in OCR fallback instead of Gemma
--vlm-url <url>       llama-server endpoint (default http://127.0.0.1:8128; reuses one already running)
--llama-server <path> Path to a llama-server binary (default: auto-detect tools/ or PATH)
--vlm-model <path>    Model GGUF (default models/gemma-4-E2B_q4_0-it.gguf)
--vlm-mmproj <path>   Vision projector GGUF (default models/gemma-4-E2B-it-mmproj.gguf)
--no-screencast       Disable screencast tracking (use screenshot polling)
--relay <url>         Connect to a relay.js host so phones work on ANY network (ws:// or wss://)
--relay-pin <code>    PIN remote phones must enter when joining via the relay
--relay-code <code>   Request a fixed room code from the relay
--chrome-path <path>  Chrome/Chromium binary to launch (default: auto-detect, incl. macOS paths)
--user-data-dir <dir> Profile dir for the launched Chrome (default ~/deck-remote-chrome-profile)
--list-tabs           Print open tabs and exit
```

## Troubleshooting

- **“Multiple tabs open”** — pass `--url docs.google.com` (or part of the
  deck's URL/file name).
- **Keywords are empty for a while** — the model is still loading on first
  launch (~a minute) or describing slides; slide 1 is always processed first.
- **Descriptions look wrong** — Gemma reads the whole slide; heavily abstract
  imagery can still produce vague descriptions. The slide number always shows.
- **“Gemma/llama.cpp unavailable”** — run `bash install.sh` (downloads
  llama.cpp + model), or point `--vlm-url` at an already-running llama-server.
  The tool keeps working with built-in OCR in the meantime.
- **Phone can't connect** — both devices must be on the same network; some
  corporate Wi‑Fi isolates clients (use a phone hotspot instead). On Linux,
  open the port: `sudo ufw allow 8675/tcp`.
- **Google Slides in edit mode** — put the deck in presentation mode first
  (`Ctrl+F5`), then restart deck-remote; the tool warns about this itself.
- **Two identical slides in a row** — screenshot tracking can't tell them
  apart; the count/next-hint may be off by one until you move again.
- **Deck changed** — restart deck-remote to re-index.

## Security

The remote is unauthenticated on your LAN by default. On shared/venue Wi‑Fi
run it with `--pin 1234`. Anyone with the URL (and pin) can control the deck —
that is the point, but choose your network accordingly.

## Website

The [GitHub Pages site](https://diegoforni.github.io/deck-remote/) hosts the
docs, an interactive demo of the phone UI, and a **connect helper**: type your
computer's `ip:port` (handy on Tailscale/ZeroTier networks) and get a tappable
link + QR for the remote. The remote itself is always served by your computer
— browsers block `ws://` WebSockets from HTTPS pages, so a web-hosted page
can't (and shouldn't) talk to your LAN server.

## Testing

```bash
bash scripts/test.sh        # e2e: HTML deck + PDF + tracking fallbacks (no AI needed)
node scripts/vlm-smoke.js   # loads Gemma and describes a synthetic slide
```
The e2e test drives a real (headless) Chromium: indexes a 6‑slide deck,
checks descriptions, presses next/back, verifies the timer, and checks that
navigation done directly in the tab (laptop keyboard) syncs to the phone —
in both screencast and screenshot-fallback tracking modes. The PDF section
is skipped automatically on builds whose headless mode lacks the PDF viewer.

## Privacy

Slide frames never leave your machine: descriptions run in a local llama.cpp
process, and the phone talks only to your computer over the LAN.

## Limitations

- One deck at a time; the deck must respond to ←/→ (Google Slides present
  mode, the Chrome PDF viewer and common HTML decks do).
- Fragments in Google Slides decks are indexed as separate steps (each
  fragment gets its own description), which usually is what you want.
- Animated overlays that appear on mouse movement may briefly confuse slide
  detection; the phone self-corrects on the next poll (~1 s).
